# Face authentication on the Dell XPS IR camera

How Omarchy turns the Windows Hello IR camera of the Dell XPS 14 (DA14260), XPS 16 (DA16260) and XPS 13 (9350, DX13260) into a second authentication method, and which layer each command owns. The user-facing pieces follow the fingerprint wizard, the lock screen gains a face context next to its fingerprint one, and the driver layer ships as a package of its own until mainline catches up.

## Hardware

The IR camera is a Himax HM1092 monochrome sensor behind the Synaptics SVP7500 USB bridge (usbio), on the same I2C bus as the RGB OV08X40. Firmware enumerates it as ACPI `HIMX1092` (one id per module variant, only the fitted one with `_STA` present and enabled), and the in-tree INT3472 driver exposes the IR flood illuminator as `/sys/class/leds/HIMX1092_00::ir_flood_led`. The TI LM3643 flash driver the DSDT also lists (`TXNW3643`) reports absent on this family.

Omarchy's kernel (`linux-omarchy` 7.2) has no sensor driver, and its in-tree `ipu-bridge` sensor table stops at the RGB sensor and the CVS device, so the IPU never gives the sensor a CSI-2 endpoint. Mainline 7.3 adds the bridge entry (`IPU_SENSOR_CONFIG("HIMX1092", 2, 180000000, 180480000)`); the sensor driver is still under review on linux-media, in two competing series. The `intel-ipu7-camera` package (Intel's out-of-tree IPU7 drivers, hardware ISP, `v4l2-relayd` into `/dev/video50`) covers RGB only, but its `intel_cvs` module performs the ownership handshake with the bridge that the IR sensor also needs.

## Layers

| Layer | Owner | Status |
| --- | --- | --- |
| Hardware detection | `omarchy-hw-dell-xps-ir-camera` | Done, tested against sysfs fixtures |
| Sensor driver and bridge entry | `hm1092-ir-camera` (`packaging/`): DKMS `hm1092` from jibsta210/svp7500-camera-fix-pack 1.0.5, DKMS `ipu-bridge-hm1092` for kernels before 7.3 | Verified on the XPS 14 (2026-10-14, Linux 7.2.5): probes, binds on CSI-2 port 2 with one lane, streams |
| Grayscale relay for Howdy | `hm1092-ir-camera`: `hm1092-relay` publishes `HM1092 IR Camera` (v4l2loopback, GRAY8, `/dev/hm1092-ir`, root's alone), hidden from PipeWire, and owns the flood LED | Verified on the XPS 14: upright, well-lit 648x368 frames (stride 1344), LED lit only while a consumer reads |
| Install on matching machines | `install/hardware/intel/ipu7-ir-camera.sh`, gated on the predicate | Done; needs the package in Omarchy's repository |
| Face matching | Howdy from the AUR, pointed at that device; `pam_exec.so` runs `omarchy-face-match` around Howdy's `compare.py` | Done by the wizard; enrolled on the XPS 14 |
| Consent | `omarchy-face-key`, a socket-activated root service that reads the Copilot key from the keyboard itself, and `default/hypr/toggles/face-key.lua`, which takes the key from every window | Tested against fake evdev nodes over a loopback stand-in for its socket; awaits a trial on the XPS 14 |
| sudo and polkit | `auth sufficient` behind the clamshell gate, like fingerprint | Done by the wizard |
| Lock screen | `/etc/pam.d/omarchy-lock-face`, a face context in `shell/plugins/lock` bounded by `/etc/omarchy/face.conf`, and `etc/sudoers.d/omarchy-face-match` for the helper's privileged half | Verified on the XPS 14 with Enter as the consent (2026-10-14); the key and the per-lock limits are unit-tested and await a trial |

## Contracts

`omarchy hw dell xps ir camera [--driver|--device] [--verbose]` is a predicate like every `hw-` command: exit 0 on a Dell XPS whose fitted camera module is the HM1092 and whose flood LED is registered, 1 otherwise, 2 on a bad flag. `--driver` additionally requires a kernel driver bound to the sensor's I2C client. `--device` implies `--driver` and prints the `/dev/videoN` whose V4L2 name contains `hm1092`, which is the device Howdy reads. `--verbose` narrates each probe on stderr. Fixture roots for tests: `OMARCHY_ACPI_DEVICES_PATH`, `OMARCHY_LEDS_PATH`, `OMARCHY_I2C_DEVICES_PATH`, `OMARCHY_VIDEO4LINUX_PATH`; the DMI match goes through `omarchy-hw-match "XPS"`.

`omarchy setup security face` runs in this order and stops at the first failure without touching later layers: hardware present, driver bound (otherwise it names the package to install), relay device available (otherwise it names the unit to check), `/usr/bin/omarchy-face-key` present, the question where the face should work (sudo, polkit and lock screen; sudo and polkit only; lock screen only), asked with `gum choose` before the long AUR builds, Howdy and pamtester from the AUR, Howdy's `compare.py` (a Howdy that ships only its native `pam_howdy.so` is refused: that module scans the moment PAM reaches it and cannot wait for the key), `device_path` set in Howdy's config, `sudo howdy add`, the key service's units in `/etc/systemd/system` with the socket enabled and the `face-key` Hyprland toggle on, verification with `sudo pamtester omarchy-face-verify $USER authenticate` through a service that asks for the face alone (`omarchy-face-match --wait`, no password prompt), exists only for that check and is removed right after, pass or fail (the user looks into the camera and presses the Copilot key), then the chosen stacks. A stack left out loses the face lines an earlier run put there, so running it again with another answer moves the face. Last, `/etc/omarchy/face.conf` is written with the lock's limits unless it exists, which also marks the setup done for the first-run invitation. Running it twice adds nothing twice and keeps an edited `face.conf`. Fixed paths are `/usr/lib/security`, `/etc/pam.d/*`, `/etc/omarchy/face.conf` and `/etc/howdy`; Howdy's layout is read from `pacman -Qlq howdy`, because the stable install is readable by root only.

Presence is not consent. A camera sees a face whether or not its owner meant to approve anything, while a fingerprint reader only answers to a deliberate touch, so a scan waits for a touch of its own: the Copilot key, read by root from the keyboard (see "The face key" below). sudo and polkit carry this block, inserted on top of their stacks:

```
auth      [success=2 default=ignore] pam_exec.so quiet /usr/bin/omarchy-hw-laptop-closed
auth      optional pam_exec.so seteuid quiet stdout /usr/bin/omarchy-face-match --hint
auth      sufficient pam_exec.so seteuid quiet stdout expose_authtok /usr/bin/omarchy-face-match
```

The gate skips both face lines while the lid is closed. The hint registers this conversation's prompt with the key service and, once it is registered, prints "Press the Copilot key to use your face, or type your password." (`seteuid`: only root reaches the service, so a hint line from an older setup offers nothing). Then `expose_authtok` makes pam_exec show the usual password prompt (sudo renders it as its own) and hand the answer to the helper on stdin. Anything typed declines the face: the helper withdraws the prompt from the key service and exits without a scan, and `system-auth`'s `pam_unix.so try_first_pass` verifies the typed password from the PAM item pam_exec stored, so there is no second prompt. The Copilot key answers the prompt with an empty line, and the helper scans only if the key service confirms the key was pressed for this very prompt; an empty Enter is just an empty password, as without face. `sudo -n` and scripts get no prompt and therefore no scan. A scan that fails or finds no model ends that round: pam_unix is handed the empty answer, rejects it, and sudo says "Sorry, try again" and starts over with the hint, at the cost of one `pam_faillock` tally; typing the password at the next prompt works as usual. A typed password costs nothing. `stdout` feeds the helper's messages to the prompt, `quiet` leaves them to the helper. Omarchy's polkit dialog does not render PAM's info messages, so `shell/plugins/polkit` here is upstream's agent reading the face line from `/etc/pam.d/polkit-1` the way it reads the fingerprint line: while PAM waits for the password with the lid open, the padlock becomes a camera and the empty field says "Face or Password"; the Copilot key, which Hyprland hands to the dialog's `polkit faceKey` IPC call, clears the field, answers with nothing and reads as "Scanning face...", a failure as "No match". Only the asking form of the line is offered. The lock service's line carries no `expose_authtok`: the lock keeps it waiting for the key instead.

The setup treats the block as one unit: a stack that carries it exactly is left alone; any other face lines, from a `pam_python` setup or from the version that scanned without asking, are stripped together with only the gate directly above them and the block is inserted fresh, so enrolled models and a fingerprint stack sharing the file both stay.

`omarchy face match` is the hidden helper behind those lines, like `omarchy-hw-laptop-closed` behind the gate. With `--hint`, and only as root, it registers the prompt with `omarchy face key wait --detach --tty` and prints the heads-up once that succeeded. Otherwise, for sudo and polkit, it reads the answer from stdin when stdin is not a terminal and either drops the prompt (`omarchy face key drop`) or takes the key's press (`omarchy face key take`); for the lock screen it waits for the key (`omarchy face key wait --lock`). With `--wait`, and only as root with a `PAM_USER`, it waits for the key itself without reading an answer: the setup's face-only check. Only then does it print "Scanning face…", run Howdy's `compare.py` for `PAM_USER` with the system Python 3, print Howdy's own messages, log to auth, and exit with Howdy's status (0 match, 10 no model, 11 timeout, 12 abort, 13 too dark). An empty or unsafe `PAM_USER` fails before anything runs; an unreadable Howdy tree means the session user's own conversation, which elevates (see the lock screen). Reached through that elevation, where sudo's `env_reset` leaves no `PAM_USER`, it refuses unless `/etc/pam.d/omarchy-lock-face` exists: the grant serves the lock screen alone, and a user who chose sudo and polkit only gets no scan through it.

`omarchy remove security face` removes the face module and only the clamshell gate directly above it from sudo and polkit, deletes the lock service, `/etc/omarchy/face.conf` and a verification service an interrupted setup left, each only where present, so it undoes any of the three setups, then stops and deletes the key service's units and turns the `face-key` toggle off, which gives the Copilot key back to the Omarchy menu, clears the invoking user's models with `howdy -U <user> -y clear` while the CLI is still installed, then drops `howdy pamtester`, plus `pam-python` and with it Python 2 where an earlier setup installed them. A failed clear stops the package drop. The user is resolved from `id`, never from `$USER`.

Without any face model, say after `howdy remove` took the last one, nothing locks anyone out: sudo and polkit still show the hint and the prompt, the key answers "No face model known" and starts the round over, and the password works at any prompt. The lock screen's attempts fail at once without lighting the LED, because Howdy checks for models before it opens the camera, while the password context is untouched. The way to stop offering face authentication is `omarchy remove security face`, which also clears the hint and the prompt.

## The face key

`omarchy face key` is the hidden service and its client, in Python like upstream's other long-lived helpers. A fingerprint reader turns a deliberate touch into the scan itself; a camera does not, so the touch is a key that no program can fake: root reads the Copilot key (evdev `KEY_F23`, which the key sends with Super and Shift) straight from each keyboard's `/dev/input/event*` node. Programs running as the user can neither read those nodes nor, without `/dev/uinput`, fake them, and keyboards made through uinput sit under `/devices/virtual`, which the service ignores. Hyprland's `face-key` toggle (`default/hypr/toggles/face-key.lua`, copied into `~/.local/state/omarchy/toggles/hypr` by `omarchy-hyprland-toggle`) rebinds the key from upstream's Omarchy menu to the polkit dialog's IPC call (`o.rebind` with `{ ipc = "polkit.faceKey" }`, like upstream's own bindings), so no window ever receives it and it can never end up in a password. A synthetic key through `hyprctl`, `wtype` or the shell's IPC reaches the dialog at most, which then answers with an empty password.

- `serve` runs as `omarchy-face-key.service` behind `omarchy-face-key.socket` (`/run/omarchy-face-key.sock`, mode 0600, root only, and the service accepts only peers of its own uid). It opens the keyboards only while a prompt waits, closes them when none does, and exits after 30 idle seconds, so outside a prompt nothing reads the keyboard. The unit allows `char-input` reads and no other device, no network, and a read-only system.
- `wait --pam-pid <pid> --user <name>` registers the PAM conversation's process (pid and start time, so a reused pid is a different prompt), logged with its command line, and waits. `--detach --tty` (the hint) returns once registered and keeps waiting in the background; on the key it answers sudo's terminal prompt with its kill character and a newline through `TIOCSTI`, which this kernel (`dev.tty.legacy_tiocsti=0`) allows to root only. pam_exec runs its command in a session of its own, where `/dev/tty` is nobody's, so the waiter opens the conversation's controlling terminal, found from its `/proc/<pid>/stat`; a conversation without one, like polkit's helper, gets no typed answer, and a terminal whose node cannot be opened fails the registration, so no hint promises a key that cannot answer. `--lock` (the lock screen) looks past sudo to the conversation that ran it, and gives up when `LOCK_WINDOW_MINUTES` from `/etc/omarchy/face.conf` have passed on the boot clock, which counts suspend. A waiter ends when its conversation's process exits or, for the lock, when the conversation closes its end of the pipe.
- `take --pam-pid <pid>` answers whether the key was pressed for that prompt within the last five seconds and consumes the press; `drop` forgets the prompt.
- One press serves exactly one waiting prompt. With several waiting, it serves none: all keep waiting, each sudo terminal and the lock screen say "Face refused: another program is waiting for the Copilot key too", and a critical notification to the user names every requester ("sudo pacman -Syu (from bash)", "a polkit dialog"). The standoff ends only when the user types a password or cancels, so a program waiting beside a real prompt never catches the press meant for it.

## The driver package

`packaging/hm1092-ir-camera` is a PKGBUILD (`makepkg -si` to try it; it belongs in Omarchy's package repository next to `intel-ipu7-camera`, which it depends on). It installs:

- `/usr/src/hm1092-<ver>`: the sensor module from the fix pack's 1.0.5 release, the one driver verified to stream and to unlock Howdy on a Dell with this bridge. It writes the sensor's hardware flip (`0x0101 = 0x03`), so frames arrive upright on the Dell. Its weak reference to a patched `intel_cvs` symbol stays unresolved against `intel-ipu7-camera`'s `intel_cvs`; the fix pack's own findings say that call is not needed.
- `/usr/src/ipu-bridge-hm1092-<ver>`: `ipu-bridge.c` from Linux 7.2.5 plus the one-line mainline entry, installed under `updates/` where depmod prefers it. `BUILD_EXCLUSIVE_KERNEL="^7\.[0-2]\."` keeps dkms from building it for 7.3 and later.
- `hm1092-camera-init.service`: `modprobe hm1092` after `intel-ipu7-camera.service` and `camera-init.service`, so the sensor binds only once `intel_cvs` owns the bridge; `hm1092-camera-deps.conf` blacklists autoload for the same reason, like `ov08x40`.
- `hm1092-relay.service`: the relay, configured by `/etc/hm1092-ir-camera.conf`. At start it links `hm1092 -> Intel IPU7 CSI2 N -> Intel IPU7 ISYS Capture M` by entity name (the port and node numbers differ between machines and boots), sets `SGRBG10_1X10/648x368` on every pad, creates the loopback with `v4l2loopback-ctl add -n "HM1092 IR Camera" -x 1` because the RGB stack already consumed the module options, holds its OUTPUT side so nothing else can inject frames, and primes it with a black frame. While a consumer is attached it lights the LED, streams the ISYS node and republishes each frame as GRAY8 (plain shift, or scaled so the 99th unsaturated percentile lands near 235); otherwise the LED is dark and the node reads black. The LED is bounded by a per-burst cap and a rolling duty budget, every wait is a `select()` with a deadline, `ExecStopPost` and the sleep hook turn it off on any exit. `hm1092-relay --probe` prints what it resolved.
- udev: `/dev/hm1092-ir` as a stable path to the relay device, which the same rule keeps root's alone (`TAG-="uaccess"`, `TAG-="seat"`, mode 0600) between `70-uaccess` and `73-seat-late`, the way `intel-ipu7-camera` hides its raw ISYS nodes; the install hooks re-trigger the device so the mode applies without a reboot, and the fix pack's rule keeping the SVP7500 bridge out of USB autosuspend. WirePlumber: `device.disabled` for the relay device, so it is an authentication sensor, not a webcam.

Testing seams: `HM1092_SYS_ROOT` and `HM1092_DEV_ROOT` retarget sysfs and `/dev` for the relay and the LED helper; `media-ctl` and `v4l2loopback-ctl` are stubbed on `PATH`. `packaging/hm1092-ir-camera/tests/test_relay.py` pins the ctypes layouts against the kernel headers and covers graph parsing, loopback lookup and creation, the LED budget, the configuration and the conversion; `test/shell.d/hm1092-ir-camera-package-test.sh` runs them and drives `--probe` and the LED helper through the seams.

## Lock screen

The lock is Omarchy's Quickshell plugin `omarchy.lock`, whose PAM conversations run in-process as the session user. `shell/plugins/lock` here is upstream's plugin with a third context added:

- `facePam` runs the `omarchy-lock-face` service. `faceConfigured` follows `/etc/pam.d/omarchy-lock-face` through a `FileView`, the way the password context follows its file: the setup writes it only after a verified enrollment, and only when the face is wanted on the lock screen, and the removal deletes it.
- While the lock offers the face, `facePam` waits for the Copilot key the way the fingerprint context waits for a finger: `syncFace()` arms it once the lock is secure, on wake, when the policy or the enrollment changes and every 30 seconds, and withdraws it once the face is no longer offered. Root scans when the key is pressed, in the dark too; the helper's "Scanning face…" line tells the lock a scan started, which wakes the display. Nothing scans on lock, wake or a timer alone, and Enter only ever submits a typed password. Howdy's own timeout ends a scan, the idle blank waits for a running one instead of cutting it short, and `faceAbortTimer` bounds a conversation that never completes; a refused key shows "Face refused" in the field, an error "Face unavailable", and a face Howdy does not know "Who are you?", which stands for ten seconds before the field says "Enter Password" once no scan is left (or returns to "Face or Password" while one is); typing clears each. Howdy reports a stranger only by its timeout and pam_exec turns every refusal into a system error, so the lock takes the helper's "Face detection timeout reached" line during a scan for a stranger, and an error without it for an unavailable face. After a miss the check waits again 1.5 seconds later if a scan is left.
- Each lock offers the face for `LOCK_ATTEMPTS` scans (default 1) within `LOCK_WINDOW_MINUTES` of locking (default 60), from root's `/etc/omarchy/face.conf`, read live; a missing file or a malformed value means the defaults. Every scan counts, a password unlock restores both for the next lock, and a scan's start reads the count and the clock afresh and stops the scan past either, since the display may have been dark, or the machine asleep, when the window closed; the key service's own bound on the boot clock covers the moments before the shell notices. A lock recovered after a shell restart offers no face: its age and spent scans died with the old shell. `FaceModel.js` holds the policy, tested in node.
- While the face is offered the empty field says "Face or Password" instead of "Enter Password", reads "Scanning face…" while a scan runs, and a camera hint sits inside the field's left edge, brighter during the scan, opposite the fingerprint hint; the password dots keep clear of both. Once the scans are spent the hint goes and the field says "Password (face failed)"; once the window has closed, "Password (face expired)".
- The user-level conversation cannot read Howdy's root-only tree, so `omarchy-face-match` re-executes its packaged copy through `etc/sudoers.d/omarchy-face-match`: `%wheel ALL=(root) NOPASSWD: /usr/bin/omarchy-face-match ""`, the same shape as upstream's `omarchy-theme-browser` and `omarchy-dns` grants. The empty argument list forbids arguments, the privileged half takes the account from `SUDO_USER`, the unprivileged half first checks that `PAM_USER` is the session user, and the outcome is a verdict for PAM, never a session.

To try it, `bin/apply-to-checkout` applies the overlay to a checkout of upstream, `omarchy dev pkg-test` installs the checkout as packages (PAM, the sudoers rule and the key service name the helpers by their `/usr/bin` paths), `omarchy dev link` points Omarchy at it, and `bin/run` walks through the setup and the manual tests. `omarchy shell lock status` then reports `face`, `faceState`, `faceAttempts`, `faceArmed` and `faceAuthenticating`, and the shell log carries `face-armed`, `face-attempt: n/limit`, `face-matched`, `face-no-match`, `face-refused`, `face-error`, `face-timeout`, `face-withdrawn` and `face-aborted` events.

## Known gaps

- The driver package has run on one XPS 14 so far (Linux 7.2.5, `intel-ipu7-camera` 1.0.6). If another machine's sensor fails to probe or stream, meros/hm1092-linux is the fallback sensor module (clean, mainline-style, both ACPI ids, but no hardware flip, so `ROTATE180=1`).
- The AUR package `intel-ipu7-ir-dkms` wraps the same fix pack but also replaces `intel_cvs` and ships the fix pack's Howdy patch; on Omarchy it would collide with `intel-ipu7-camera`, which is why this package takes only the sensor module.
- The key closes what the Enter left open: no program running as the user can start a scan, through sudo, pkexec or the lock's sudoers grant, without a finger on the keyboard. What remains is the fingerprint's own gap. A press when no prompt of the user's own is waiting goes to whichever prompt is, so the key is for answering a prompt on screen, never for trying out. A program that keeps a prompt waiting can also hold off the face for every real prompt, since each press is refused; the password still works.
- The Copilot key stops opening the Omarchy menu while the face is set up; Super + Space still does.
- sudo's prompt is answered by injecting into its terminal, so face works where sudo asks on the terminal; `sudo -S` and a graphical askpass fall back to the password.
- The IR module has no privacy LED, and the RGB camera's cannot stand in: the V4L2 core claims a sensor's privacy LED when the sensor registers (`v4l2_subdev_get_privacy_led()` calls `led_sysfs_disable()`), so writes to `/sys/class/leds/OVTI08F4_00::privacy_led/brightness` fail with `EBUSY` and only the RGB sensor's own streaming lights it. Only the prompt's or the lock screen's own text shows an IR scan.
- Upstream's `omarchy-remove-security-fingerprint` deletes every `omarchy-hw-laptop-closed` line, including the face gate. Its sed should delete only the gate directly above `pam_fprintd.so`, the way the face removal does.
- `pamtester` and `howdy` are AUR packages; `python-dlib` builds for a while. Howdy has not tagged a release since 2.6.1 (2020) although its beta with a native PAM module merged into master in 2025; `howdy-git` and the C++ `howdy-next` on the AUR are the candidates if the stable package falls behind.
- Howdy opens the relay device through OpenCV, which reaches it via FFmpeg's video4linux input. FFmpeg prints `ioctl(VIDIOC_QBUF): Bad file descriptor` when Howdy releases the capture, because it returns the last frame buffer after closing the device. Harmless; the frames were already read.

## Exit plan

Linux 7.3 already lists the sensor in `ipu-bridge`; the package's bridge override stops building there on its own. Once a sensor driver lands in `linux-omarchy` as well, drop the `hm1092` DKMS tree and keep the relay, the units, Howdy, the PAM lines and the lock plugin; nothing else depends on which driver wins, only on the device name contract above.
